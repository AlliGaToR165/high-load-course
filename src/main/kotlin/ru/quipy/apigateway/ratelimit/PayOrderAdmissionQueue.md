# Очередь допуска оплаты

## Зачем она нужна

Платёжный провайдер ограничивает число одновременных запросов и запросов в секунду. Если отклонять каждый запрос сверх мгновенного лимита, короткий всплеск нагрузки превращается в `429`, хотя часть запросов ещё можно выполнить до их дедлайна. Если же складывать их в большую очередь исполнителя, они занимают ресурсы и могут попасть к провайдеру уже слишком поздно.

`PayOrderAdmissionQueue` держит **ограниченную очередь перед платёжной работой**: ждут только запросы, для которых по текущей оценке ещё остаётся время. Вход в неё находится в [`APIController.payOrder`](../APIController.kt#L65-L78). Метод возвращает `DeferredResult`, поэтому HTTP-поток не занят ожиданием места в очереди. Ответ с `PaymentSubmissionDto` означает, что работа **поставлена на выполнение**, а не что провайдер уже завершил оплату.

## Как устроен допуск

1. При запуске контроллер получает [`PaymentAccountProperties`](../../payments/config/PaymentAccountsConfig.kt#L39-L55): `parallelRequests`, `rateLimitPerSec` и `averageProcessingTime` для выбранных аккаунтов. Это данные провайдера, а не измеренная приложением задержка. Поскольку [`PaymentSystemImpl`](../../payments/logic/PaymentServiceImpl.kt#L24-L28) вызывает аккаунты последовательно, бюджет обработки складывается из их средних времён; для нескольких аккаунтов добавлен запас на ожидание rate permit. Число одновременно запущенных платежей ограничено также [размером пула `OrderPayer`](../../payments/logic/OrderPayer.kt#L18-L36). Расчёт находится в [полях контроллера](PayOrderAdmissionQueue.kt#L51-L66).
2. [`submit`](PayOrderAdmissionQueue.kt#L90-L126) проверяет дедлайн, жёсткий предел очереди и [динамический предел](PayOrderAdmissionQueue.kt#L156-L175). Если обозначить расчётное время обработки через `R`, оставшееся время до дедлайна через `D`, запас через `S`, а устойчивую скорость выпуска через `v` запросов/с, то ориентир для ожидающих: `k = floor(v × (D − R − S))`. `v` ограничена и `rateLimitPerSec`, и числом параллельных запросов относительно `R`. Например, при одном аккаунте, `parallelRequests = 5`, `R = 4,9 с`, лимите `10/с`, `D = 60 с` и `S = 1 с` получается `v ≈ 1,02/с` и `k = 55`. Код дополнительно оценивает ожидание по занятым слотам и секундным окнам аккаунтов. Запрос, который можно запустить сразу, не обязан занимать место в динамической очереди.
3. Один [`dispatchRequests`](PayOrderAdmissionQueue.kt#L177-L222) удаляет отменённые/просроченные записи и берёт следующий запрос из FIFO, только если свободен слот и есть предварительные разрешения для всех аккаунтов. После [резервирования слота](PayOrderAdmissionQueue.kt#L227-L250) он передаёт обработку в ограниченный `handoff`-пул, чтобы сам диспетчер не ждал операций с БД. [`OrderPayer.processPayment`](../../payments/logic/OrderPayer.kt#L39-L58) запускает платёжную работу в своём пуле; `onFinished` освобождает слот **после завершения всей работы**, а не после HTTP-ответа.
4. Предварительный допуск не гарантирует точное время реальных вызовов: аккаунты вызываются последовательно, а задержки могут различаться. Поэтому непосредственно перед HTTP-запросом [адаптер вызывает `awaitCall`](../../payments/logic/PaymentExternalServiceImpl.kt#L56-L72). [Второе, фактическое секундное окно](PayOrderAdmissionQueue.kt#L128-L154) того же контроллера соблюдает лимит конкретного аккаунта и не ждёт дольше, чем позволяет дедлайн с учётом его среднего времени обработки.

При переполнении или невозможности уложиться в дедлайн очередь возвращает [`429` с `Retry-After`](PayOrderAdmissionQueue.kt#L266-L277). Жёсткий предел, запас времени и значение заголовка задаются в [`application.properties`](../../../../../resources/application.properties#L44-L46). Метрики: `payment_admission_queued`, `payment_admission_inflight`, `payment_admission_wait`, `payment_admission_rejected`.

Ограничения: расчёт опирается на **среднее** время, поэтому не гарантирует дедлайн для каждого запроса; очередь и окна находятся в памяти одного процесса и не координируют несколько реплик приложения.
